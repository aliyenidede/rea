# Contributing

readev-tools is an npx installer: `src/` places files into a host project, and `templates/` +
`core/` hold the actual content it places. Keep that split in mind before you change anything.

## Setup

```bash
git clone https://github.com/aliyenidede/rea.git
cd rea
# nothing to install for the installer itself — zero runtime deps, and tests use node:test
# (built into Node >=18), so npm test works with no npm install step
pip install -e ".[dev]"   # only needed if you're touching the frozen rea-dev Python shim (rea/, tests/)
```

Requires Node.js **>=20** (see `engines` in `package.json`). Python 3.11+ is only needed for the
`rea/`/`tests/` shim.

## Running the test suite

```bash
npm test          # node --test --test-concurrency=1 test/*.test.js
```

Run it **serially** — `--test-concurrency=1` is not optional. Some tests swap sibling modules on
disk (e.g. stubbing `src/place.js` for a `src/setup.js` test) and will corrupt each other's state
under concurrency. Don't drop the flag when running a subset of tests either.

If you touch `rea/` or `tests/` (the frozen Python shim):

```bash
ruff check .
ruff format --check .
pytest
```

`ruff` is pinned in `pyproject.toml`'s `[project.optional-dependencies].dev` so CI is
deterministic — don't upgrade it casually.

## Try the installer without publishing

```bash
node bin/readev-tools.js setup .          # run it against this repo, or any target path
node bin/readev-tools.js verify .
node bin/readev-tools.js migrate . --dry-run
```

This repo dogfoods its own installer — `.claude/` and `.gemini/` here are *install output*, not
hand-authored.

## The one rule that matters most: edit `templates/`, never `.claude/`

**The installer is dumb, the prompts are smart.** `src/` only copies files, resolves ownership,
and edits shim files between managed markers — it makes no workflow decisions. All actual
behavior (what a slash command does, what an agent prompt says) lives under `templates/commands/`
and `templates/agents/`.

`.claude/` and `.gemini/` in this repo are generated by running the installer against itself. If
you want to change what a command or agent does:

1. Edit the source under `templates/commands/` or `templates/agents/` (or `core/` for the
   tool-agnostic trio: `principles.md`, `craft-checklist.md`, `rea-schema.md`).
2. Re-run `node bin/readev-tools.js setup .` to regenerate `.claude/`/`.gemini/` from the new
   source.
3. Never hand-edit `.claude/` directly — the next `setup` run overwrites anything the installer
   owns, and your change would silently vanish.

Same logic for shim files (`AGENTS.md`, `CLAUDE.md`, `.gemini/settings.json`): the installer only
touches the region between the `readev-tools:start` / `readev-tools:end` markers. Content outside
those markers is the host project's own and is never overwritten. Do not write a second pair of
those marker comments into prose anywhere — the installer treats a file with more than one pair as
ambiguous and refuses it.

## Filesystem writes go through `src/safe-path.js`

Every write, move, or delete the installer performs must be containment-checked through
`src/safe-path.js` (`resolveInsideRoot`, `isRealpathInsideRoot`, or `isInsideRoot` depending on the
call site's existing failure semantics — see the module and
[docs/decisions/0002-safe-path-hardening.md](docs/decisions/0002-safe-path-hardening.md) for which
to use). This closed a CWE-59 symlink/junction-escape class where a planted symlink inside a
target project could redirect a write outside the project root. A new mutation path that bypasses
`safe-path.js` is a **security regression**, not a style nit — flag it in review, don't wave it
through.

## Branch and PR workflow

- Never push to `main` directly.
- Work on a branch named `feature/*`, `fix/*`, `chore/*`, `docs/*`, or `hotfix/*`.
- Open a PR against `main`.
- The `test` check (GitHub Actions, `.github/workflows/ci.yml`) must pass before merge — branch
  protection on `main` requires it.
- `staging` exists in the workflow triggers but has been dormant; target `main`.

## Where things live

```
bin/readev-tools.js   # npx entry point
src/                   # installer core: cli, setup, place, shims, prune, manifest,
                        # verify, migrate, settings-surgery, legacy-scan, rea-archive, safe-path
test/                   # node:test suites, one per src/ module + templates.test.js
core/                   # tool-agnostic content shipped to hosts: principles, craft-checklist,
                        # rea-schema
templates/              # what the installer places: AGENTS.md, per-tool shims, .rea/ scaffold
  commands/              # the slash commands (the product)
  agents/                # agent prompts + skill-writer-patterns.md
rea/, tests/            # frozen rea-dev 0.7.3 Python shim (PyPI signpost only, no new features)
docs/                   # public decision record (docs/decisions/)
```

If you're not sure whether a change belongs in `src/` (mechanics) or `templates/`/`core/`
(workflow content), it almost always belongs in `templates/`/`core/`. `src/` should stay
boring — file operations only.

## Commit and PR checklist

Before opening a PR, check `.github/PULL_REQUEST_TEMPLATE.md` — it covers: tests pass locally,
you edited `templates/`/`core/` rather than `.claude/`, you branched off `main`, and
`docs/`/`CHANGELOG.md` are updated if the change is user-visible.

## Reporting a bug

Use the bug report issue template (`.github/ISSUE_TEMPLATE/bug_report.yml`) — it will ask for
your Node version, which AI tool you're using, and the output of `npx readev-tools verify`.

## Security issues

Do not open a public issue for a vulnerability. See [SECURITY.md](SECURITY.md).
